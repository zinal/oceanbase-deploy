# Кластер OceanBase на физических хостах с IPv6-only

Как поставить кластер OceanBase на физические серверы, у которых в сети данных есть только IPv6. `./scripts/deploy.sh` для такого контура не годится: он создаёт ВМ в Yandex Cloud и отдаёт в OBD адреса IPv4. Первые три узла собирает `scripts/23-bootstrap-cluster.sh`, следующие — `scripts/21-expand-observer.sh` и `scripts/22-expand-obproxy.sh`. OCP и OBD для этого не нужны.

Ниже — ограничение продукта, набор версий и порядок установки. Размеры CPU, RAM, NVMe и схема «3 Zone / один `observer` на сервер» те же, что в [крупном физическом кластере](large-physical-cluster-recommendations.md).

## Короткий вывод

| Вопрос | Ответ |
|---|---|
| Можно ли поднять IPv6-only кластер | Да, начиная с сборок, где есть параметр `use_ipv6`. Для линии этого репозитория это **oceanbase-ce 5.0.1** |
| Можно ли сделать это текущим `./scripts/deploy.sh` | Нет |
| Штатный путь без OCP и OBD | `23-bootstrap-cluster.sh` поднимает первые три узла (`ALTER SYSTEM BOOTSTRAP`). Дальше `21-expand-observer.sh` / `22-expand-obproxy.sh` |
| OCP | Не обязателен. Имеет смысл, если нужна веб-консоль. Версия не ниже 4.3.6-CE, и на этом билде хост должен приниматься по IPv6 |
| Путь через OBD «как есть» | Не считать готовым. В опубликованных плагинах OBD до oceanbase 4.6 список Root Service для IPv6 собирается без квадратных скобок, а observer такой список не разбирает |
| Смешать IPv4-клиентов и IPv6-кластер на одном порту 2881 | Нельзя. При `use_ipv6` SQL-сокет создаётся с `IPV6_V6ONLY` |

Практический порядок: `scripts/23-bootstrap-cluster.sh` собирает первые три узла, дальше расширение — `scripts/21-expand-observer.sh` и `scripts/22-expand-obproxy.sh`. Всё это без OCP и OBD. Управляющую машину, которая качает RPM, оставить с выходом в IPv4 или положить пакеты на локальное зеркало. Сами серверы БД могут не иметь IPv4-маршрута в интернет.

## Что говорит продукт

Поддержка IPv6 в Community Edition видна по исходникам тега `v5.0.1_CE` и по более ранним тегам `v4.2.5_CE_BP3`, `v4.3.1_CE_BETA`, `v4.3.5_CE_BP2`: параметр кластера `use_ipv6` (по умолчанию `False`, меняется только перезапуском). Флаг процесса `-6` / `--ipv6` выставляет тот же режим. Адрес узла задаётся `-I` / `local_ip` и после старта кластера не меняется.

OCP описывает это как отдельный сценарий, а не как «любая версия, у которой есть флаг»:

- OCP **V4.3.6** (enterprise и [OCP 4.3.6-CE](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/download-center/opensource/ocp/4.3.6_CE/OCP%204.3.6-CE%20Release%20Notes.pdf)): полное управление кластером на IPv6-адресах.
- OceanBase: **[V4.2.5 BP3 Hotfix3, V4.3.0)** или **[V4.3.5 BP2 Hotfix1, +∞)**. Сборка **5.0.1.0** попадает во второй интервал, и в `v5.0.1_CE` параметр `use_ipv6` есть.
- OBProxy: **V4.3.4 и новее**. В комплекте All-in-One 5.0.1 из [README](../README.md) это OBProxy 4.3.6 BP1. У прокси есть `local_bound_ipv6_ip` (по умолчанию `::`).
- OBClient: **V2.2.9 и новее**.
- Сервис Binlog по IPv6 OCP не разворачивает.

Релиз Community 4.3.1 отдельно пишет «предоставлена поддержка формата IPv6». Документ systemd-установки той же ветки ещё говорит, что поле `ip` в `/etc/oceanbase.cnf` IPv6 не принимает. Ориентир для продакшена — матрица OCP 4.3.6, а не фраза из обзора 4.3.1.

FAQ по развёртыванию V4.3.1 (страница по-прежнему опубликована):

- Один `observer` не умеет RPC по IPv4 и SQL по IPv6. Без `use_ipv6` процесс IPv6 не слушает. С `use_ipv6` на SQL-порту включается `IPV6_V6ONLY`, и IPv4-клиент на этот порт не подключится. То же видно в коде: `IPV6_V6ONLY` ставится и в RPC (`deps/oblib/src/rpc/pnio/nio/inet.c`), и в SQL NIO (`ob_sql_nio.cpp`).
- Узлы с IPv4 и IPv6 в одном кластере FAQ разрешает, но у IPv4-узла ОС и сеть всё равно должны уметь IPv6, иначе до IPv6-соседей он не дойдёт. Для сети, где IPv4 нет, это не схема: **все** `observer`, `obproxy`, OCP и клиенты сидят на IPv6.

Формат адреса в списке Root Service разбирает `ObInnerConfigRootAddr::parse_rs_addr` (тег `v5.0.1_CE`):

```text
IPv4:  a.b.c.d:rpc_port:sql_port
IPv6:  [a:b:c:d:e:f:g:h]:rpc_port:sql_port
```

У OBProxy в том же комментарии один порт, SQL: `[ipv6]:sql_port`. Сжатая запись (`2001:db8::11`) для самого observer допустима: разбор идёт через `inet_pton`. Скобки обязательны там, где после адреса стоит `:порт`.

## Где ломается OBD

Актуальный разбор `servers.ip` в [obdeploy `_deploy.py`](https://github.com/oceanbase/obdeploy/blob/master/_deploy.py) принимает либо IPv4, либо IPv6 **ровно из восьми групп** без `::` и без скобок:

```text
^([0-9a-fA-F]{1,4}:){7}[0-9a-fA-F]{1,4}$
```

`2001:db8::11` эта проверка отвергает. В YAML адрес ещё и надо брать в кавычки: двоеточие ломает разбор.

Плагин `plugins/oceanbase/4.6.0.0/start_pre.py` (самый новый oceanbase-плагин в публичном дереве OBD на момент сверки) собирает список так:

```text
-r '<ip>:<rpc_port>:<mysql_port>;...'
```

Квадратных скобок нет. Для IPv6 observer такой список не разбирает, bootstrap не начинается.

Ключ `ipv6` в том же файле превращается в аргумент `-6 <значение>`. У процесса `-6` — флаг без значения, лишний токен ему не нужен. Рабочий параметр бинаря называется `use_ipv6` и уходит в `-o`. В `parameter.yaml` плагина oceanbase до 4.6 этого имени нет (оно объявлено у seekdb). Попадёт ли `use_ipv6: true` в командную строку конкретного All-in-One, надо смотреть уже установленный плагин:

```text
~/.obd/plugins/oceanbase-ce/<версия>/start_pre.py
```

Пока в этом файле нет скобок вокруг IPv6 в `-r` и нет передачи `use_ipv6`, OBD не является путём установки. Ответ 2024 года «OBD режет любой IPv6, вырежьте regex» устарел: полный восьмигрупповый адрес парсер уже пропускает, но до рабочего кластера этого мало.

All-in-One 5.0.1 несёт OBD 4.5.0 и OCP-CE 4.4.2. OCP-CE 4.4.2 новее 4.3.6, где IPv6 объявили, но в найденных заметках 4.4.2 это отдельно не повторено. На установленном OCP первым делом добавить один хост по IPv6. Если форма отклоняется, брать OCP 4.3.6-CE, для которого сценарий описан явно.

## Сеть на хосте

Нужен один стабильный адрес на сервер: глобальный или ULA (`fc00::/7`). Его и писать в `local_ip`.

Если `local_ip` пустой, а `use_ipv6` включён, процесс сам берёт адрес с `devname` (`ObNetUtil::get_local_addr_ipv6`): global и ULA предпочтительнее link-local и loopback. При нескольких адресах одного уровня остаётся первый из `getifaddrs`, порядок не зафиксирован. Временные адреса SLAAC (`use_tempaddr`) для узла БД не подходят: `local_ip` после старта не меняется.

На каждом хосте:

- статический адрес на интерфейсе данных, без зоны `%eth0`;
- `net.ipv6.conf.<if>.accept_ra=0` и `use_tempaddr=0`, если адрес задан вручную;
- link-local только для канала, не для RPC 2882 и не для SQL;
- chrony по IPv6, расхождение часов между узлами меньше 100 мс;
- SSH по литералу IPv6, на управляющей машине `AddressFamily inet6`;
- loopback `127.0.0.1` оставить. Документация не описывает хост, на котором выключен весь IPv4, включая loopback. Его используют локальные проверки и часть обвязки. «IPv6-only» здесь значит: на интерфейсах данных и в маршрутах кластера нет IPv4.

`clockdiff` в проверке хоста OCP ходит ICMP TIMESTAMP. Это механизм IPv4. На IPv6-only проверку выключить: `ocp.host.check.clock-diff.enable=false`. Синхронизацию часов закрывает chrony, не clockdiff. В облачном контуре этого репозитория та же проверка уже обходится отдельно, см. [развёртывание OCP](ocp-deployment.md).

Порты между узлами и с клиентов: TCP 2881 (SQL), 2882 (RPC), 2886 (obshell), 2883 (obproxy), 8088 (obagent), 8080 (OCP), 22 (SSH). Плюс chrony.

Пакеты OceanBase качаются с зеркал, которые часто доступны только по IPv4. Управляющий хост может быть dual-stack или иметь локальную копию RPM. На серверы БД пакеты попадают по SSH поверх IPv6. Выход серверов БД в IPv4-интернет не нужен.

Диски, sysctl памяти, swap off, один `observer` на машину, отдельный Clog — как в [рекомендациях по физическому кластеру](large-physical-cluster-recommendations.md). Блок `net.ipv4.*` из `scripts/02-prepare-servers.sh` на этот контур не переносить.

## Схема

```text
клиенты
    │  TCP [vip]:2883
    ▼
L4 (F5 / LVS / HAProxy mode tcp), VIP только IPv6
    │
    ├── obproxy × 3+     отдельные хосты, local_bound_ipv6_ip = стабильный адрес
    │
    ├── observer zone1   N хостов, один процесс, local_ip = стабильный адрес
    ├── observer zone2   столько же
    └── observer zone3   столько же

OCP × 1 (или 3 за своим IPv6 VIP) — отдельный хост, не на observer
```

Три Zone одинаковой ёмкости, не больше семи Zone на bootstrap. `obproxy` не ставить на те же машины, что и нагруженный `observer`. Binlog-сервис в эту схему не входит.

L4 — обычный TCP, без HTTP и без session persistence. Health-check порта 2883. Idle timeout не короче, чем у приложений. В HAProxy адрес пишется в скобках:

```text
bind [2001:db8:1::50]:2883
server obp1 [2001:db8:1::21]:2883 check
```

Клиенты ходят на VIP, не на список `observer:2881`.

## Путь 1. Пилот из трёх узлов

Цель пилота — убедиться, что выбранный RPM слушает IPv6 и собирает Paxos. Три физических сервера, три Zone, по одному `observer`. Диски и память — по документу о физическом кластере, на пилоте можно меньше, но не ниже минимума продукта (4 CPU, 16 ГБ RAM).

До скрипта на каждом хосте уже должны быть: статический адрес, SSH, один и тот же каталог с `bin/observer` (RPM `oceanbase-ce` 5.0.1 и libs, без `obd cluster deploy`) и смонтированные каталоги данных и Clog. Сам скрипт диски не размечает.

```bash
./scripts/23-bootstrap-cluster.sh --print \
  --zone1 2001:db8:1::11 \
  --zone2 2001:db8:1::12 \
  --zone3 2001:db8:1::13
./scripts/23-bootstrap-cluster.sh --yes \
  --zone1 2001:db8:1::11 \
  --zone2 2001:db8:1::12 \
  --zone3 2001:db8:1::13 \
  --ssh-user obadmin --ssh-key ~/.ssh/id_ed25519
```

`--print` ничего не меняет. `--yes` по SSH запускает процесс на каждом адресе и с первого узла выполняет bootstrap. У всех трёх один и тот же `-r`, и этот узел в списке есть — иначе собраться некому. Для IPv6 флаг `-6` без лишнего аргумента, в `-o` есть `use_ipv6=true`, адреса в скобках:

```text
-r '[2001:db8:1::11]:2882:2881;[2001:db8:1::12]:2882:2881;[2001:db8:1::13]:2882:2881'
```

SQL, который скрипт шлёт на zone1:

```sql
ALTER SYSTEM BOOTSTRAP
  ZONE 'zone1' SERVER '[2001:db8:1::11]:2882',
  ZONE 'zone2' SERVER '[2001:db8:1::12]:2882',
  ZONE 'zone3' SERVER '[2001:db8:1::13]:2882';
```

Сессия с `ob_query_timeout` в один час: создание sys-тенанта на больших дисках не укладывается в десятки секунд. Скрипт ждёт `ACTIVE` у всех трёх до 15 минут. Смешивать IPv4 и IPv6 в этой тройке нельзя. Порты 2881 и 2882 после старта не менять.

Если первый запуск оборвался и clog уже не пуст, повтор — `./scripts/23-bootstrap-cluster.sh --yes --wipe ...`. `--wipe` останавливает свой `observer` и очищает data/redo только на этих трёх адресах. На кластере, который уже собрался, `--wipe` стирает данные.

Приёмка после `ACTIVE`:

- `ss` показывает 2881 и 2882 на IPv6, а не на `0.0.0.0`;
- с четвёртого хоста `obclient -h 2001:db8:1::11 -P2881` открывает сессию, подключение по IPv4 на тот же порт не проходит;
- останов одного из трёх узлов оставляет SQL доступным;
- в `DBA_OB_SERVERS` три строки, адреса совпадают с назначенными, а не с временным SLAAC-адресом.

OBProxy на пилоте ставится следом: `./scripts/22-expand-obproxy.sh`. Версия не ниже 4.3.4, `local_bound_ipv6_ip` равен стабильному адресу прокси, `rootservice_list` в виде `[2001:db8:1::11]:2881;[2001:db8:1::12]:2881;[2001:db8:1::13]:2881`. Клиент ходит на 2883 этого прокси.

Дальнейшие `ADD SERVER` / `DELETE SERVER` / `STOP SERVER` используют ту же форму `'[ipv6]:2882'`, не голый адрес с двоеточиями. Документ [восстановления узла](node-recovery.md) написан на примерах IPv4; меняется только запись адреса.

## Расширение без OCP и OBD

OCP для членства узла не нужен. OBD тоже: он только копирует RPM и вызывает те же SQL. Добавление observer — это пустой процесс с `-r` на уже живые узлы и одна команда:

```sql
ALTER SYSTEM ADD SERVER '[2001:db8:1::21]:2882' ZONE 'zone1';
```

`DELETE SERVER` и замена узла у OBD вообще не автоматизированы, их и в облачном контуре этого репозитория делают SQL. Скрипты ниже делают только расширение и не ходят в Yandex Cloud.

Пока кластер ещё из трёх пилотных узлов, новый сервер готовится так же: тот же RPM в `/home/obadmin/observer`, отдельные `/data/1` и `/data/log1`, статический IPv6. С управляющей машины:

```bash
export OB_ROOT_PASSWORD='…'   # пусто, если root@sys без пароля
./scripts/21-expand-observer.sh --print \
  --ip 2001:db8:1::21 --zone zone1 \
  --rs 2001:db8:1::11,2001:db8:1::12,2001:db8:1::13
./scripts/21-expand-observer.sh --yes \
  --ip 2001:db8:1::21 --zone zone1 \
  --rs 2001:db8:1::11,2001:db8:1::12,2001:db8:1::13 \
  --ssh-user obadmin --ssh-key ~/.ssh/id_ed25519
```

`--print` ничего не меняет. `--yes` по SSH запускает `bin/observer` на новом хосте (флаг `-6` без лишнего аргумента, в `-o` есть `use_ipv6=true`, список `-r` в скобках и без адреса самого нового узла) и сразу выполняет `ADD SERVER` с `ob_query_timeout` в один час. Короткий таймаут по умолчанию (10 с) даёт ERROR 4012, а повтор по уже записавшему clog — ERROR 4179. Если 4179 всё же вышел, повтор только с `--wipe`: очищаются data/redo **этого** узла, seed не трогается.

Скрипт ждёт `ACTIVE` в `DBA_OB_SERVERS` и сравнивает адрес по значению, а не по строке, так что сжатая и полная формы совпадают. `UNIT_NUM` тенанта он не увеличивает: лишний сервер в zone без нового unit нагрузку не возьмёт. Это отдельный `ALTER RESOURCE`, когда ёмкость действительно нужна.

OBProxy в кластер SQL не входит. Второй скрипт только поднимает процесс и печатает строку для L4:

```bash
./scripts/22-expand-obproxy.sh --print \
  --ip 2001:db8:1::31 --name obp4 \
  --rs 2001:db8:1::11,2001:db8:1::12,2001:db8:1::13
```

Для IPv6 в параметры попадает `local_bound_ipv6_ip`. В backend HAProxy строка имеет вид `server obp4 [2001:db8:1::31]:2883 check`.

Чего эти скрипты не делают: установку RPM, разметку дисков, смену `local_ip` у уже вступившего узла, удаление сервера и перенос unit. Первая тройка — `scripts/23-bootstrap-cluster.sh`. Удаление — `STOP SERVER`, при необходимости `MIGRATE UNIT`, затем `DELETE SERVER` с тем же скобочным адресом.

## Путь через OCP

OCP нужен только как консоль. Кластер без него живёт. Если консоль всё же ставится, это отдельный хост и версия не ниже 4.3.6-CE; расширение можно по-прежнему делать скриптами выше, не через UI.

1. Отдельный хост OCP: 4+ CPU и 16+ ГБ RAM, лучше с запасом из [профиля OCP](ocp-deployment.md). Сеть хоста — тот же IPv6, что у кластера.
2. Поставить OCP 4.3.6-CE или новее. Если берётся OCP-CE 4.4.2 из All-in-One 5.0.1, первым шагом добавить тестовый хост по IPv6 и убедиться, что адрес принят.
3. Выключить проверку clockdiff (`ocp.host.check.clock-diff.enable=false`).
4. Добавить физические хосты по IPv6 и SSH-порту 22. Несколько адресов в мастере OCP разделяются запятой.
5. Создать кластер: OceanBase из матрицы выше (для этого репозитория — 5.0.1), OBProxy ≥ 4.3.4, на каждом узле явный `local_ip`. Binlog не включать.
6. Перед пулом `obproxy` поставить IPv6 VIP на L4.
7. Масштабирование — теми же скриптами расширения. UI OCP для этого не обязателен. В операциях, где адрес вводится вручную, писать `[ipv6]:2882`.

OCP с метаданными в том же кластере требует, чтобы мета-тенанты тоже жили на IPv6-узлах. Отдельный IPv4-кластер «только под OCP» в IPv6-only сети не из чего собрать.

## Что не делать

- Не направлять `./scripts/deploy.sh`, Terraform и `generated/obd-cluster.yaml` этого репозитория на эти хосты. Генератор подставляет IP из инвентаря Yandex Cloud как есть и не включает `use_ipv6`.
- Не оставлять в OBD-yaml сжатый адрес и не писать его без кавычек.
- Не рассчитывать, что имя хоста в поле `ip` сработает: OBD по-прежнему требует адрес, не hostname.
- Не подключать старых IPv4-клиентов к порту 2881 или 2883 этого кластера. Нужен IPv6 у приложения или отдельный шлюз, который сам говорит с кластером по IPv6. Шлюз не возвращает двойной стек на сокете OceanBase.
- Не использовать link-local и временные адреса как `local_ip`.
- Не планировать Binlog Service на этих адресах.

`./scripts/deploy.sh` по-прежнему только для IPv4 в Yandex Cloud. Первые три узла физического IPv6-кластера — `scripts/23-bootstrap-cluster.sh`, расширение — `scripts/21-expand-observer.sh` и `scripts/22-expand-obproxy.sh`.
